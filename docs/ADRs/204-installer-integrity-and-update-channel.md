# Installer integrity and update channel

**ID:** ADR-204
**Status:** Accepted (amended 2026-05-24 — see Amendment 1; amended 2026-05-25 — see Amendment 2)
**Date:** 2026-05-22
**Supersedes:** —
**Superseded by:** —
**Related:** ADR-101, ADR-201, ADR-301, ADR-302, ADR-409

## Context

The platform is shipped as a local-first Electron workbench (ADR-101 / ADR-301). End users (mental-health practitioners) install it on their own Windows or Linux machine and run it indefinitely. There is no server-side rendering or hosted UI; every behaviour change reaches a user only as a new binary on that user's device.

Five user-facing expectations frame the decision:

1. A public website lists per-platform downloads (Windows installer, Linux `.deb`).
2. The app surfaces an "update available" indication.
3. Updates install without re-running the full website-download flow.
4. A user who skipped several versions can jump straight to the current version.
5. After an update lands, the first run shows a changelog for what changed.

Constraints that bias the design:

- PHI never leaves the device in plaintext (ADR-301). Update artefacts contain code only, no PHI, so they are safe to host publicly.
- The renderer is a composition shell (ADR-102); it may not own networking authority and must not call `electron-updater` directly.
- Electron is pinned at `^41.2.2` until `better-sqlite3-multiple-ciphers` supports V8-14 (O157). Auto-update tooling must accept Electron 41.
- `Implementation_Plan.md` §"What this plan deliberately does not cover" parked the update channel for "a later phase when the feature surface stabilises". The post-Phase-9 / Phase-10 baseline is sufficiently stable to commit it now.

The platform must also pick a posture on regressions. Two roads:

- **Roll-forward only** — bad releases are fixed by shipping a newer release. Auto-update carries users out. No downgrade tooling.
- **Rollback** — the app supports pulling a user back to an earlier version, either by re-installing the prior binary or by a built-in downgrade path.

`electron-updater` has no first-class downgrade. The clinical local-only data store (ADR-302, SQLCipher under Phase 10b) carries schema migrations whose reverse path is not guaranteed loss-free. Forcing a downgrade therefore risks corrupting user data — a strictly worse outcome than a known bad version.

## Decision

The platform commits a single end-to-end release-and-update story:

### 1. Distribution targets

- **Windows:** NSIS installer (`.exe`) only. No portable executable. The installer registers Add/Remove Programs entry, Start Menu shortcut, and file associations.
- **Linux:** Debian package (`.deb`) only. AppImage is dropped from this point on (it was the Phase 4 stop-gap target).
- **macOS:** not in scope of this ADR. Lands when O170 (macOS `.icns`) is resolved and a macOS build host exists.

### 2. Artefact store

GitHub Releases is the authoritative artefact store. Every release tag produces, at minimum:

- `Ru-Soam-Setup-<version>.exe` (NSIS)
- `ru-soam_<version>_amd64.deb`
- `latest.yml` (Windows update manifest, generated by `electron-builder`)
- `latest-linux.yml` (Linux update manifest)
- `release-notes-<version>.md` (changelog excerpt for this version)

The published release body contains the changelog excerpt verbatim.

### 3. Public website

The marketing / download site lives in `apps/web/` of this monorepo and is deployed on Cloudflare Pages. Reasons for monorepo placement:

- The release tag drives both the desktop build and the website deploy.
- `CHANGELOG.md` is read by both the in-app "what's new" modal (bundled at build time) and the website.
- One PR can ship a version bump, changelog update, and any website copy change atomically.

Download buttons point at GitHub's stable `…/releases/latest/download/<asset>` URLs. GitHub resolves those to the current release's assets, so the website does not redeploy per release.

### 4. Update mechanism

The Main process owns the update lifecycle, using `electron-updater`:

- On app start (after a short delay) and on a periodic timer, Main calls `autoUpdater.checkForUpdates()` against the appropriate `latest*.yml` on GitHub Releases.
- `electron-updater` always reads the **current** manifest, so a user N versions behind moves directly to `latest` in a single download (expectation 4).
- The renderer learns about update state through a typed platform capability (ADR-103) and corresponding event channel (ADR-202). The renderer never invokes `electron-updater` directly.
- The user-facing "update available" indication is delivered through the StatusBar alert mechanism (ADR-409) — the same surface used for other in-app alerts — not a separate banner. The specific alert UI is owned by the StatusBar alert design; this ADR only commits the data path.

### 5. Per-platform update UX

- **Windows (NSIS):** seamless. Download in background → user confirms → `electron-updater` invokes the NSIS installer in silent mode → app relaunches on the new version. This is the default `electron-updater` path.
- **Linux (`.deb`):** **download-and-guided-install.** `electron-updater` downloads the `.deb` to the user's data directory. The app then presents the user with the path and a copyable `sudo apt install ./<file>.deb` instruction (or opens the file in the system's default `.deb` handler if one is registered). A self-installing background path is deliberately out of scope — installing a `.deb` requires elevation that the running app cannot grant itself in-place without an APT repository.

A future APT repository (per O173 below) would convert this to a fully background path. It is not committed here.

### 6. Roll-forward only

The platform adopts **roll-forward only** as policy:

- `electron-updater` is configured with no downgrade path.
- Bad releases are remediated by shipping a newer release (`v1.2.4` after a broken `v1.2.3`). Auto-update carries users out.
- A user who needs to manually downgrade may do so by re-installing an older `.exe` / `.deb` from GitHub Releases, but this is an unsupported escape hatch — the app gives no UI for it and makes no guarantees about local data after a downgrade across a schema migration.

Roll-forward is paired with two risk-reduction mechanisms:

- **Staged rollouts via prereleases.** A release candidate is published as a GitHub *prerelease* tag (e.g. `v1.2.3-beta.1`). `electron-updater` is configured by default not to surface prereleases. A future Settings toggle (O174) lets willing users opt into the prerelease channel.
- **Forward-fix discipline.** A bad release is fixed by an immediate follow-up release within hours, not by triaging a rollback.

A version-floor / kill-switch (server-told "minimum supported version") is acknowledged but deferred (O175). It depends on a backend the MVP does not yet have.

### 7. Changelog single-source

`CHANGELOG.md` at the repo root, in Keep-a-Changelog format, is the single source of truth for human-readable release notes. The release pipeline (Phase A below) parses the section matching the release tag and emits two artefacts:

- `release-notes-<version>.md` — uploaded to the GitHub Release body.
- `changelog.json` — bundled into the desktop app at build time. Includes the last N versions (initially N = 10) so the post-update modal works offline.

### 8. Post-update changelog modal

On every renderer boot, the renderer compares `app.getVersion()` (read through a capability) against a persisted `lastSeenVersion` value in the local Store (ADR-302). On mismatch:

- Fetch the entries from the bundled `changelog.json` for the range `(lastSeenVersion, currentVersion]`.
- Render a modal listing the entries.
- On dismiss, write `currentVersion` into `lastSeenVersion`.

The version range form supports expectation 4 (users who skipped intermediate versions see the union of changes).

### 9. Integrity and signing

- **Windows:** the NSIS installer **should** be Authenticode-signed. Until a certificate is acquired (O172), the installer is delivered unsigned — users will see Windows SmartScreen warnings. This is an MVP-acceptable degradation; signing lands before public release.
- **Linux:** the `.deb` **should** be GPG-signed and verifiable by `dpkg-sig` (O172). Until then, the `.deb` is shipped unsigned and the website documents the SHA-256 of each asset.
- The `electron-updater` manifests (`latest*.yml`) carry SHA-512 checksums for each asset; tampering at GitHub would be detected at update time.

ADR-301's PHI boundary is unaffected — update artefacts are code only.

## Consequences

### Positive

- A single artefact store (GitHub Releases) feeds the website's download buttons, the auto-updater, and the published release notes. No drift between channels.
- The renderer remains a composition shell — `electron-updater` is owned by Main and surfaced through a typed capability + event, consistent with ADR-103 / ADR-202.
- The bundled `changelog.json` keeps the post-update modal offline-safe.
- Roll-forward removes a whole class of corruption risk that a downgrade across a SQLCipher schema migration would carry.
- Staged rollouts via prereleases give a cheap incident-mitigation lever without building a kill-switch service.

### Negative

- Linux update flow is two-step (download + guided install) until an APT repo (O173) is built. Friction is real but bounded; a simple in-app instruction defangs it.
- Roll-forward only means a bad release can affect users until the next release ships. The mitigation is operational (release within hours), not architectural.
- Unsigned binaries trigger SmartScreen / dpkg warnings until O172 lands. Users may bounce on the first install.
- The website lives in the monorepo, so a website-only typo fix carries the desktop build through CI. Cheap on net but worth noting.

### Neutral

- The website's download URLs depend on GitHub's `…/releases/latest/download/…` redirect surviving. If GitHub changes that, the website needs a redirect layer; the desktop auto-update does not (it talks to a versioned manifest).

## Considered Options

- **Self-hosted artefact store (S3 / R2)** — _Rejected for MVP_: requires running a bucket, ACLs, and an HTTP layer in front. GitHub Releases gives the same shape for free and ships `electron-updater` integration out of the box. Revisit if (a) a Pro plan limit is hit, or (b) sovereignty / geographic distribution becomes a constraint.
- **Mac App Store / Microsoft Store** — _Rejected for MVP_: revenue cut, signing constraints, slower review loop, no Linux equivalent. Stores are a packaging *target*, not a primary distribution channel.
- **AppImage (Linux) instead of `.deb`** — _Rejected_: AppImages do not integrate with Linux package managers and have a weaker update story. `.deb` is what the target user (Ubuntu / Debian practitioner) expects.
- **Own APT repository for Linux from day one** — _Rejected for MVP_: real infra (signed metadata, key rotation, mirroring). Not justified before user pain confirms the guided-install step is unacceptable. Deferred (O173).
- **Rollback (downgrade) supported in-app** — _Rejected_: `electron-updater` does not support it cleanly; SQLCipher schema migrations are not guaranteed reversible; the risk of corrupting local PHI is greater than the risk of waiting for a forward-fix. Revisit only post-incident.
- **In-app banner for update notifications** — _Rejected_: alert real estate is owned by the StatusBar alert mechanism (ADR-409). Reusing it keeps the platform's notification surface single-sourced.
- **Renderer drives `electron-updater` directly** — _Rejected_: violates ADR-102 (renderer owns no authority) and ADR-202 (renderer reaches Main only through `window.soam`). Update lifecycle lives in Main.

## Amendment 1 (2026-05-24): artefact host → Cloudflare R2 (generic provider)

**Trigger.** The source repository (`meersajidh/new-ru-soam`) is and stays **private**. GitHub release-asset visibility is inherited from the repository, so the §2/§3/§4 plan — public `…/releases/latest/download/…` URLs and public `latest*.yml` — returns **404 to anonymous clients**. That breaks both the website's download links and the shipped `electron-updater` feed (verified: anon `GET` on the asset and the API both 404). The original "self-hosted S3/R2" option was rejected for MVP on cost/effort grounds; the private-source constraint reverses that trade-off.

**Decision.** Release artefacts are hosted on **Cloudflare R2** behind a public bucket URL, consumed via `electron-updater`'s **`generic`** provider. The source repo stays private; only the code-only artefacts (installers + manifests, no PHI per ADR-301) are public.

This overrides:

- **§2 Artefact store** — Cloudflare R2 bucket (public read) replaces GitHub Releases. The same five artefacts per release (`*.exe`, `*.deb`, `latest.yml`, `latest-linux.yml`, plus `*.blockmap`) are uploaded to the bucket root. Channel manifests for prereleases (`beta.yml` / `beta-linux.yml`) are written by `electron-builder` from the semver prerelease component and uploaded alongside.
- **§3 Website download URLs** — point at `<R2_PUBLIC_URL>/<asset>` (stable) and the version-pinned beta assets. The site is built **full-B**: `apps/web/build.mjs` fetches `latest.yml` / `latest-linux.yml` (and `beta*.yml` when present) from the public bucket at build time and injects version, filenames, sizes, and checksums. No runtime fetch.
- **§4 Update mechanism** — `electron-updater` reads `latest*.yml` from the R2 public URL (`provider: generic`). The lifecycle, capability surface, and StatusBar-alert data path are unchanged (provider-agnostic).
- **§6 Staged rollouts** — prereleases are distinguished by the `electron-updater` **channel manifest** (`beta.yml`) derived from the `-beta.N` tag, not by a GitHub "prerelease" flag (no GitHub Release exists). `allowPrerelease=false` keeps stable clients on `latest`.
- **§9 Integrity** — the website publishes the **SHA-512** carried in the `electron-updater` manifest (the canonical hash the updater verifies), not a separately-computed SHA-256. Signing (O172) is unaffected.

**Publish pipeline change.** `electron-builder`'s `generic` provider is download-only; CI builds with `--publish never` and uploads `release/*.{exe,deb,yml,blockmap}` to R2 over the **S3-compatible API** (R2 endpoint `https://<account-id>.r2.cloudflarestorage.com`, region `auto`). No GitHub Release is created; the website is the changelog surface (§7's `release-notes-*.md` GH-body upload is dropped; `changelog.json` bundling is unchanged).

**Roll-forward implication.** The bake-in feed URL (`app-update.yml`) is effectively permanent for an installed version. The R2 public URL must be fixed **before** the first release that ships on this channel. `v0.1.0` (built against the private GH provider) has a dead updater; the first R2 release becomes the working baseline.

**Unchanged:** §1 targets, §5 per-platform UX, §7 changelog single-source (minus the GH-body step), §8 post-update modal.

## Amendment 2 (2026-05-25): package manager → npm; native packaging; dependency-cooldown

**Trigger.** The shipped Windows installers for v0.1.0–v0.1.2 crashed at launch with `Failed to load native binding`, and v0.1.3 additionally broke Linux with `Module did not self-register` (the packed `better_sqlite3.node` was built for `NODE_MODULE_VERSION` 137 / Node 24, but Electron 41 requires 145). Root cause: the project used **pnpm** with its default **isolated** linker, so `apps/desktop/node_modules` deps were symlinks into the `.pnpm` store. `electron-builder`'s file collector follows symlinks on Linux but **not junctions on Windows** → native modules (`@node-rs/argon2`, `better-sqlite3-multiple-ciphers`) never reached `app.asar` on the Windows leg. A `pnpm deploy --node-linker=hoisted` workaround produced a flat tree but did **not** rebuild its natives against the Electron ABI (the deploy's `install-app-deps` rebuilt the *workspace* copy, not the deployed copy) — and it polluted the workspace install-state. Three distinct pnpm-specific packaging failures in two sessions; `node-linker=hoisted` is a dead end in a pnpm *workspace* (it hoists to the repo-root `node_modules`, leaving the app package bare).

**Decision.** Migrate the monorepo from pnpm to **npm (npm workspaces)** for the desktop packaging path. npm lays out a **flat, real-directory** `node_modules`: the only modules packed into `app.asar` are the two native ones (real dirs → no symlink/junction problem on Windows), and the app's `postinstall` rebuilds them against the **Electron** ABI in that tree (mechanism in **Native rebuild** below). The pnpm-deploy script (`apps/desktop/scripts/package.mjs`) is deleted; packaging reverts to a plain `electron-builder --config electron-builder.yml` invocation. `asarUnpack` (`**/*.node` + the two native package trees) is retained as defence-in-depth. The renderer-only workspace package `@ru-soam/editor` is Vite-bundled into `dist/` and never packed, so its workspace symlink is irrelevant to packaging.

This overrides the **publish pipeline change** in Amendment 1 only in mechanism (still `--publish never` + S3-upload to R2; the build command is plain electron-builder, no deploy step). Everything else in ADR-204 + Amendment 1 stands.

**Toolchain changes.** `pnpm-workspace.yaml` + `pnpm-lock.yaml` removed; root `package.json` gains `"workspaces": ["apps/*","packages/*"]`, drops the `packageManager` field (use Node 24's bundled npm), and rewrites `pnpm --filter X` scripts to `npm run X -w ru-soam`. `@ru-soam/editor` dep changes from `workspace:*` to `*`. CI (`release.yml`, `web-deploy.yml`) drops `pnpm/action-setup`, uses `cache: npm` + `npm ci` + `npm run build -w ru-soam` + `npx wrangler@4`. `justfile` + `.husky/pre-commit` use npm. `package-lock.json` is committed; CI uses `npm ci`.

**Native rebuild (postinstall).** The Electron-ABI rebuild is done by `apps/desktop/scripts/rebuild-natives.mjs` (postinstall = `node scripts/rebuild-natives.mjs`), which calls `@electron/rebuild` (devDep) directly. **`electron-builder install-app-deps` was tried first and rejected:** in postinstall under npm workspaces it shells out to `npm install` in the app dir (and mis-detects the workspace root as `undefined`), which re-fires the same postinstall → **unbounded recursion / fork-bomb** (observed ~150 stacked processes). The script avoids this — it never runs an install, only a rebuild. The npm flat hoist puts the two native packages in the **repo-root** `node_modules` while their dependency is *declared* in `apps/desktop/package.json`; `@electron/rebuild` ties module *discovery* to `buildPath`'s `package.json` and module *location* to `projectRootPath`, so the script sets `buildPath = apps/desktop` and `projectRootPath = repo root`. With both equal (the default) discovery and location disagree under the hoist and the rebuild **silently no-ops while reporting success** — so the verification gate checks the `.node`'s embedded ABI (`node_register_module_v145`) + an `ELECTRON_RUN_AS_NODE` load, never the tool's exit code. `onlyModules` covers `better-sqlite3` and its `better-sqlite3-multiple-ciphers` alias (both carry a `.node`); `@node-rs/argon2` is napi/Node-API (ABI-stable) and is not rebuilt. The earlier electron pin to exact `41.6.1` (for version detection) is retained but not sufficient on its own. (O191.)

**Supply-chain (replaces pnpm's `minimumReleaseAge`, which npm core lacks).** A dependency-version **cooldown** is enforced at the *update* layer, not at install: **Renovate** (`renovate.json`, `minimumReleaseAge: "7 days"`, `internalChecksFilter: strict`) and **Dependabot** (`.github/dependabot.yml`, `cooldown.default-days: 7` for npm + github-actions). With a committed lockfile + `npm ci`, installs are deterministic; new versions only enter via cooldown-gated PRs. **Delta from pnpm:** pnpm's `allowBuilds` (approve-list for native postinstall scripts) has no npm equivalent — npm runs all lifecycle scripts (needed for electron/better-sqlite3 builds); the install-script surface is accepted and gated instead by the version cooldown + lockfile review (O191).

**First working baseline = v0.1.4.** v0.1.2 (published, Windows-dead) and v0.1.3 (published, both-dead) are burned and superseded; their R2 manifests must be pulled so clients don't roll forward into them. Verification gate (was skipped for v0.1.3): the packaged binary is **launched** and an `ELECTRON_RUN_AS_NODE` ABI check confirms the packed `.node` loads under Electron (ABI 145) before tagging.

## Open Items

- **O186** — R2 bucket public-access surface. MVP uses the managed `r2.dev` URL or a custom domain (`dl.ru-soam.com`, gated on the deferred `ru-soam.com` setup). Custom domain + cache rules to be finalised when the domain lands.
- **O187** — R2 artefact retention / lifecycle policy. Roll-forward keeps all historical installers reachable (the manual-downgrade escape hatch of §6); a retention rule (e.g. keep last N majors) is deferred until storage cost warrants it.
- **O191** — npm install-script surface (Amendment 2). npm runs all lifecycle scripts (no pnpm `allowBuilds` equivalent). Mitigated for now by the Renovate/Dependabot 7-day cooldown + committed `package-lock.json` + `npm ci`. Revisit if a stricter gate is wanted (e.g. `npm ci --ignore-scripts` + an explicit rebuild allowlist, or `--foreground-scripts` auditing). Also: Renovate and Dependabot both open update PRs — scope one (likely Dependabot → security-only) if the duplication is noisy.
- **O188** — Manifest/asset integrity in transit to R2. The S3-upload step trusts CI; a post-upload checksum verification (re-fetch `latest*.yml`, confirm asset SHA-512) is deferred. Tampering at rest in R2 would still be caught by `electron-updater` at install (manifests carry SHA-512).
- **O172** — Code signing. Windows Authenticode certificate + Linux GPG signing for `.deb`. Lands before public availability. Until then, SHA-256 of each asset is published on the website and the user is warned about SmartScreen.
- **O173** — Own APT repository for Linux (hosted on Cloudflare R2 or similar). Converts the Linux update from "download + guided install" to fully-background `apt upgrade`. Lands when the guided-install friction is observably blocking adoption.
- **O174** — Prerelease (beta) channel UI. A Settings toggle that flips `electron-updater`'s `allowPrerelease`. Out of scope until Settings surface lands (Phase 12).
- **O175** — Version-floor / kill-switch. A backend-told "minimum supported version" that the app refuses to run below. Out of scope until a backend exists (post-Phase 11).
- **O176** — Linux background update. Background install path for `.deb` updates without elevation prompts (e.g. via the APT repo of O173 or a packaged-with-app polkit rule). Strict superset of O173's effect.
- **O177** — _Resolved by [ADR-308](308-update-time-data-integrity.md)._ Migration policy under roll-forward, pre-migration backup, transactional DDL, and schema-version gates are committed in ADR-308 §2–§5.
- **O178** — Update-check failure UX. What does the app show when the update server is unreachable, returns a malformed manifest, or fails checksum verification? Tied to the StatusBar alert surface; specifics owned by that design.
